# 从个人项目到可维护开源项目的升级路线

当前定位：本地研究与 Data Engineering 学习项目。0.2.0 的重点是让陌生贡献者能独立运行、理解数据契约、复现错误并验证发布。生产成熟度需要持续维护和运行证据，不能用一次重构或版本号替代。

## 0.2.0：本轮交付

- 可离线体验：12 个品种的确定性合成行情、独立演示库、已有数据拒绝写入、双表事务。
- 清晰接口：参数校验、UTC 日期范围、空数据与错误状态、标准 JSON 图表对象。
- 安全验证：忽略真实 .env、隔离文件 SQLite、阻止测试联网，统一配置/迁移/测试入口。
- 可重复协作：Django 5.2 LTS、依赖版本快照、跨 OS/Python CI、Issue/PR 模板、依赖更新 PR。
- 可检查发布：源码 ZIP/tar.gz、SHA-256、版本/标签/提交一致性检查，验证成功后发布 GitHub Release。
- 延续现有完整历史/近期批次校验、事务回滚和历史覆盖保护。

本轮不需要更换数据库。SQLite 足以支撑当前本地使用，先收集性能与并发数据再决定是否更换。

## 优先级与验收标准

| 顺序 | 具体问题 | 最小方案 | 可验证结果 |
| --- | --- | --- | --- |
| 1：采集可观测性 | 失败日志和返回 0 难以追踪 | CollectionRun 与逐品种结果，记录 run_id、provider、请求窗口、市场窗口、行数、开始/结束、状态、错误类别 | 成功/失败/回滚均可追溯，失败不会显示为成功；先写隔离迁移测试 |
| 2：近期数据覆盖与新旧顺序 | 非空但短缺/陈旧快照可能被接受，旧任务可能晚完成 | 按品种、市场日历与请求窗口制定覆盖契约；提交时检查候选批次时间和最后成功 run | Mock Clock 测试周末、假日、时区、迟到批次、合法窗口滚动及真实截断 |
| 3：唯一性与查询性能 | 去重仅限应用导入器，表无唯一约束 | 在备份副本上审计重复数据，拟定人工可审查清理方案，再添加 symbol/date 唯一约束与索引 | 隔离迁移往返、重复写入拒绝；解释查询计划与性能，不自动清理真实库 |
| 4：独立调度进程 | 无显式单进程生命周期与跨进程锁 | management command + BlockingScheduler + UTC + OS/DB 锁，优雅退出与失败退出码 | 不启动真实任务的受控 scheduler 测试；并发两个进程只能一个持有锁；web 导入无启动副作用 |
| 5：增量持久化与来源 | 全量替换成本增长，难以确认修订来源 | 用测量结果决定增量 upsert；区分 market_timestamp 和 ingested_at，保留批次摘要及数据修订政策 | 合成重放与交叠数据可重复导入；修改前后查询一致；大批次内存/耗时有基准 |
| 6：供应链与运维 | 当前仅版本约束与校验和 | 依赖漏洞审查、完整 hash lock、发布签名/证明、备份恢复演练、监控和支持政策 | 以实际扫描结果和恢复演练记录作验收，不承诺未核实的安全性 |
| 7：真正的多来源能力 | 多个来源的市场语义可能不同 | 只有接入第二个具体来源时才抽取 Provider 协议；保留各自窗口、频率和授权契约 | 两个离线适配器跑同一套契约测试；明确 ticker、时区与 OHLC 调整语义差异 |
| 8：公开服务 | 本地应用缺少公共流量边界 | 单独评估认证、访问控制、限流、分页/点数限制、TLS/代理、生产服务器和数据许可 | 部署审查、负载与恢复演练；禁止把 runserver 当成生产服务 |

## 建议 PR 划分

下一项选“采集运行记录”，先做只记录和查询状态的最小版本，避免同时改 scheduler、导入算法和数据库约束。每项 PR 都应包含问题复现、最小修改、失败注入、兼容性说明及下一项建议。

记录模型属于新增迁移，先确认旧库升级路径，再决定是否可上线。历史去重、精度迁移等不可逆操作必须单独评审，不能借升级静默处理。

## 贡献者体验与维护节奏

- README 的离线路径作为每次发布的人工验收流程；CI 覆盖支持的平台和 Python 版本。
- 每个 bug 先给最小合成复现，数据完整性问题必须测试事务失败和重复执行。
- Dependabot 只提出更新 PR；维护者审查版本与 CI 后合并。
- 每次发布维护 changelog、行为变化、已知限制和支持范围；0.x 不暗示稳定公共 API。
- 用 Issues 收集真实需求和运行反馈，以修复可复现问题、文档可用性和维护响应衡量成熟度。
